# Trinity website progressive-disclosure rebuild

Date: 21 November 2026
Repository: jamos467-prog/trinityengine.ai; production-removal checkout; main.
Scope: public website only. Preserve existing GitHub Pages deployment.

## Objective
Reduce first-visit cognitive load with a coherent narrative, one captured-interface gallery and deeper technical material revealed on request. Target at least 25–30% less default scrolling without reducing text legibility. Keep every established content anchor usable.

## Accepted architecture
1. Hero: clear product purpose and short ACi explanation.
2. See Trinity at work: one manual gallery, five categories (Workspace, Reasoning, Knowledge, Operations, Agents); one capture at a time; thumbnail selection, previous/next, enlargement, keyboard access; no autoplay.
3. Reason: ENG/SYNTH/PRIME and replaceable inference; deeper reasoning architecture nested.
4. Remember: persistent context, LTKG and consolidation; topology and mathematical research nested.
5. Coordinate: Radar, Raven research and evidence-backed work; reorganization details nested.
6. Govern: authority, policy, provenance and cryptographic implementation status.
7. Develop: operating architecture distinguished from Coding UI, Forge and federation development.
8. Explore: research documents, Tiny_Trinity, symbolic vocabulary and optional technical explanations.
9. Existing waitlist and bottom-left after-hours artwork.

## Non-negotiable content contracts
- Only Cortex issues coding-agent build orders. Ravens research on Cortex request; the user briefs Trinity and sees coding activity in a read-only mirror.
- ENG/SYNTH/PRIME are Cortex roles, not Raven identities.
- Captures are recorded application state. Conceptual/edited imagery remains labelled individually.
- Preserve pending public-key/signing status and unverified Forge/federation benchmark status.
- Do not imply API traffic measures reasoning quality or provider names are a fixed number of active streams.
- Preserve current gallery assets, technical demonstrations, source/provenance explanations and existing fragment identifiers.
- Keep native disclosure content available without JavaScript; JS enhances gallery and deep-link selection.

## Verification method
Measure loaded page scrollHeight with no fragment and default-closed disclosures, at identical viewport widths. Image width/height attributes reserve layout. Expanded content is intentionally excluded from the initial-reading comparison. Record actual figures rather than claiming the requested percentage without measurement.

## Risks and mitigations
- Legacy JS can conflict with gallery visibility: replace old gallery handlers, retain unrelated demo handlers.
- Nested sections may inherit excessive spacing: scope new disclosure styles and preserve standalone document styles.
- Fragment targets can be hidden: reveal ancestors before scrolling; select matching gallery slide on initial load and hash changes.
- Hiding content can harm discovery: short descriptive summaries, explicit topic links and keyboard-operable native details.
- Build status is distinct from product status: website publication does not change application functionality.
